Chapter 3 — Describing Syntax & Semantics

Concepts of Programming Languages · Quick Reference

§1 · Foundations

📖 Core Definitions

SyntaxThe form of expressions, statements, and program units — what is legal to write.
SemanticsThe meaning of those expressions, statements, and program units.
Sentence / StatementA string of characters that belongs to a language.
Sentential formAny string in a derivation, including the start symbol. May contain nonterminals.
LexemeThe lowest-level syntactic unit (e.g., index, +, 17).
TokenA category of lexemes (e.g., identifier, int_literal, plus_op).

⚙️ Recognition vs. Generation

RecognizerReads a string and accepts or rejects it. The syntax analyzer (parser) in a compiler is a recognizer.
Generator (Grammar)Produces sentences of the language. Easier for humans to read and understand.
Key insightThere is a close mathematical relationship between generators and recognizers for the same language — this discovery drove compiler theory.
A grammar can be algorithmically converted to a recognizer (e.g., via yacc — Yet Another Compiler Compiler).
§2 · BNF / Context-Free Grammars

🔬 BNF Anatomy

MetalanguageA language used to describe another language. BNF is a metalanguage.
NonterminalAn abstraction / variable in the grammar. Written in <angle brackets>. Can be replaced.
TerminalA literal lexeme or token. Cannot be replaced further.
Production / RuleLHS → RHS. The LHS nonterminal is defined by its RHS.
Start symbolThe topmost nonterminal (often <program>). Derivation begins here.
DerivationSequence of rule applications starting from the start symbol until only terminals remain.
<assign> → <id> = <expr> <id> → A | B | C <expr> → <expr> + <term> | <term> <term> → <term> * <factor> | <factor> <factor> → ( <expr> ) | <id>
This unambiguous grammar gives * higher precedence than + because * is deeper in the tree (farther from start symbol).

🌲 Parse Trees

Parse treeA hierarchical tree showing the syntactic structure of a sentence derived from a grammar.
Internal nodesLabeled with nonterminal symbols.
Leaf nodesLabeled with terminal symbols.
SubtreeDescribes one instance of an abstraction in the sentence.
Every derivation with an unambiguous grammar has a unique parse tree, but that tree can be represented by both a leftmost and a rightmost derivation.
Leftmost derivation — replace leftmost NT first Rightmost derivation — replace rightmost NT first

⚠️ Ambiguity

Ambiguous grammarA grammar that generates a sentence with two or more distinct parse trees.
Why it mattersCompilers base code generation on parse trees. Multiple trees → undefined meaning.
DetectionIf a sentence has more than one leftmost (or rightmost) derivation, the grammar is ambiguous.
Classic exampleThe dangling else problem: if(a) if(b) S else S — does else match the inner or outer if?
SolutionRewrite the grammar to be unambiguous using extra nonterminals (e.g., <matched> vs <unmatched> statements), or handle in the compiler.

🔢 Operator Precedence & Associativity

PrecedenceOperators lower in the parse tree have higher precedence (evaluated first).
AssociativityDetermines evaluation order when two operators have equal precedence.
Left associativityAchieved with left recursion: rule LHS appears at the start of its own RHS.
<expr> → <expr> + <term>
Right associativityAchieved with right recursion: LHS appears at the end of RHS.
<factor> → <exp> ** <factor>
Warning: Left recursion prevents some important parsing algorithms from working. The grammar must then be transformed, and associativity enforced by the compiler instead.
§3 · EBNF Extensions

📝 EBNF — Three Extensions

Extension Symbol Meaning BNF Equivalent
Optional part [ ] The enclosed part may appear 0 or 1 times Two rules: one with the part, one without
Repetition { } The enclosed part may repeat 0 or more times (replaces recursion for lists) Recursive rule with two alternatives
Multiple choice ( a | b | c ) Choose exactly one option from the group Three separate rules joined by |
-- BNF (verbose, recursive): <expr> → <expr> + <term> | <expr> - <term> | <term> -- EBNF (compact, iterative): <expr> → <term> {(+ | -) <term>}
Note: EBNF does not increase the descriptive power of BNF — it only improves readability and writability. Also, the EBNF repetition form does not explicitly encode left associativity; the parser must enforce it.
§4 · Attribute Grammars

🏷️ Static Semantics

Static semanticsLanguage rules about legal form that are checked at compile time but are hard or impossible to describe in BNF.
Hard in BNFType compatibility rules (e.g., can't assign float to int in Java).
Impossible in BNF"All variables must be declared before use."
Dynamic semanticsThe meaning of constructs during execution — covered in §5.

🧩 Attribute Grammar Components

AttributeA value associated with a grammar symbol (like a variable). Set A(X) = S(X) ∪ I(X).
Synthesized attr.Computed from a node's children. Information flows up the tree.
Inherited attr.Computed from a node's parent and siblings. Information flows down/across.
Intrinsic attr.Synthesized attributes of leaf nodes whose values come from outside the parse tree (e.g., the symbol table).
Semantic functionComputes attribute values. Attached to grammar rules.
Predicate functionA Boolean check on attributes. If false → static semantic violation.
Fully attributedA parse tree where all attribute values have been computed. Process called decorating.

📌 Attribute Grammar Example — Type Checking

Grammar rules:

<assign> → <var> = <expr> <expr> → <var> + <var> | <var> <var> → A | B | C

Attributes:

actual_typeSynthesized on <var> and <expr>. Stores int or real.
expected_typeInherited on <expr>. Set from the LHS variable's type.

Semantic & predicate rules:

Rule 1 (assign): <expr>.expected_type ← <var>.actual_type Rule 2 (expr → var+var): <expr>.actual_type ← if both vars are int → int else → real Predicate: actual_type == expected_type Rule 4 (var → A|B|C): <var>.actual_type ← look-up(var.string)
Evaluation order must respect dependencies. If both inherited and synthesized attributes exist, a dependency graph is needed.
§5 · Dynamic Semantics — Three Approaches

🔭 Overview — Three Semantic Description Methods

Method Based on Core idea Useful for Weakness
Operational Lower-level programming language / virtual machine Describe meaning by showing what happens when you run it on an idealized machine Language users, informal descriptions in textbooks Depends on another language; can become circular. Complex like VDL for PL/I = useless.
Denotational Recursive function theory (mathematics) Map language constructs to mathematical objects (functions/sets) Rigorous language specification; most widely known formal method Complex, hard to write for real languages; of little use to ordinary users
Axiomatic Mathematical logic / predicate calculus Define what can be proven about a program using pre/postconditions Proving program correctness; reasoning about programs during construction Very difficult for complex statements (loops); limited practical use for compilers

⚙️ Operational Semantics

1
Design an intermediate language whose every construct has an obvious, unambiguous meaning.
2
Build a virtual machine (interpreter) for that language.
3
Describe target language constructs by translating them into the intermediate language and running them.
C for loop → operational meaning: for (expr1; expr2; expr3) { ... } expr1; loop: if expr2 == 0 goto out ...body... expr3; goto loop out: ...
Natural — final result only Structural — full step-by-step trace

📐 Denotational Semantics

Syntactic domainThe set of syntactic structures being mapped (input to mapping function).
Semantic domainThe mathematical objects that represent meaning (output).
State sA set of ordered pairs: s = {<i₁,v₁>, <i₂,v₂>, …}. Represents current variable values.
VARMAP(i, s)Returns the value of variable i in state s.
Binary number example (Mbin maps syntax → decimal): Mbin('0') = 0 Mbin('1') = 1 Mbin(<bin_num> '0') = 2 * Mbin(<bin_num>) Mbin(<bin_num> '1') = 2 * Mbin(<bin_num>) + 1 Assignment (Ma maps state → state): Ma(x = E, s) = s' where x gets Me(E, s)
Key difference from operational: state changes defined by mathematical functions, not coded algorithms. Does not model step-by-step execution.

✅ Axiomatic Semantics — Key Concepts

Assertion / predicateA logical expression about program variables. Written in {braces}.
PreconditionAssertion that must hold before a statement executes.
PostconditionAssertion that holds after a statement executes.
Weakest preconditionThe least restrictive precondition that guarantees the postcondition. Written wp(S, Q).
AxiomA logical statement assumed true (inference rule with no antecedent).
Inference ruleIf S₁…Sₙ are true, then S can be inferred. Used for sequences, selections, loops.

📋 Axiomatic Rules Summary

Assignment Axiom
{Qx→E} x = E {Q}

Weakest precondition = Q with all x replaced by E

Example: a = 2*y - 3 {a > 25} → substitute: 2*y - 3 > 25 → y > 14 → WP = {y > 14}
Rule of Consequence
{P} S {Q}, P' ⇒ P, Q ⇒ Q' ───────────────────────────── {P'} S {Q'}

Postcondition can be weakened. Precondition can be strengthened.
Sequence Rule
{P1} S1 {P2}, {P2} S2 {P3} ───────────────────────────── {P1} S1; S2 {P3}

Work backwards: compute WP of S2 first, then use it as postcondition for S1.
While Loop Rule
{I and B} S {I} ─────────────────────────────────────── {I} while B do S end {I and (not B)}

I = loop invariant Must satisfy all 4 criteria →

🔄 Loop Invariant — 4 Criteria

1
P ⇒ I — The precondition implies the invariant (invariant is true before loop starts).
2
{I and B} S {I} — Invariant is preserved by the loop body (stays true through each iteration).
3
(I and not B) ⇒ Q — Invariant + exit condition together imply the postcondition.
4
Loop terminates — Without this, we only have partial correctness. With it: total correctness.
How to find I: Compute wp(body, Q) for 0, 1, 2, 3 iterations. Look for the pattern. The invariant is usually a generalized version of those preconditions.

🔀 Selection (if-else) Rule

Inference Rule for if B then S1 else S2
{B and P} S1 {Q}, {(not B) and P} S2 {Q} ───────────────────────────────────────────── {P} if B then S1 else S2 {Q}
Both branches must be proven. Find the precondition of each branch separately. If they differ, use the rule of consequence to strengthen the weaker one to match.

⚡ Common Exam Pitfalls & Key Facts

Topic What to remember
Syntax vs SemanticsSyntax = form (what you can write). Semantics = meaning (what it does). Well-designed language: semantics follows directly from syntax.
BNF vs EBNFEBNF adds [], {}, (a|b). Same expressive power as BNF — only readability improves.
Precedence in grammarHigher precedence → operator appears lower in parse tree / farther from start symbol.
Left vs right recursionLeft recursive rule = left associative. Right recursive = right associative. Exponentiation is usually right associative.
Dangling elseClassic ambiguity. Resolved by matching else with nearest preceding unmatched if. Requires separate matched/unmatched nonterminals in grammar.
Synthesized vs InheritedSynthesized flows UP (from children). Inherited flows DOWN (from parent/siblings). Both = need dependency graph for eval order.
Assignment axiomCompute WP by substituting the RHS expression for the LHS variable in the postcondition.
Partial vs Total correctnessPartial = loop does the right thing IF it terminates. Total = correct AND terminates.
Most widely known formal semanticsDenotational semantics.
First formal use of operational semanticsVDL (Vienna Definition Language) for PL/I — turned out too complex to be useful.
Axiomatic semantics devised byFloyd (1967), further developed by Hoare (1969). Based on predicate calculus / formal logic.
Denotational semantics based onRecursive function theory (mathematics). Scott & Strachey (1971).
