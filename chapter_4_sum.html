Why Separate Lexical from Syntax?

Simplicity: Lexical analysis is simpler — handle it separately so the syntax analyzer is smaller and cleaner.

Efficiency: Lexical analysis is a big chunk of compile time; separating it lets you optimize it specifically.

Portability: Lexical analyzers deal with platform-specific file I/O. Syntax analyzers can be platform-independent.

Why Use Formal Grammars (BNF)?

1. BNF is clear and concise for both humans and software.

2. The BNF description can be used as the direct basis for writing a parser.

3. Implementations based on BNF are easier to maintain (modularity).

4.2

Lexical Analysis

Term Definition Example from: result = oldsum - value / 100;
Lexeme The actual character string extracted from the source code. The raw text. result, =, oldsum, -, value, /, 100, ;
Token The category/type code assigned to a lexeme. Usually an integer constant. IDENT(11), ASSIGN_OP(20), IDENT(11), SUB_OP(22)…
Symbol Table Database of names built by the lexical analyzer. Stores user-defined names and their attributes (e.g., variable type). result → {type: float}, oldsum → {type: int}…
Character Class A group of characters treated the same way. Used to simplify state diagrams (e.g., LETTER covers all 52 letters, DIGIT covers 0–9). LETTER, DIGIT, UNKNOWN
State Diagram A directed graph (finite automaton) where nodes = states, arcs = transitions on input characters. Describes how tokens are recognized. Start → (LETTER) → collecting name → (non-LETTER/DIGIT) → return IDENT

3 Ways to Build a Lexical Analyzer

1 — Software Tool (e.g., lex)

Write formal token descriptions using regular expressions. Feed them into a tool like lex (UNIX) which auto-generates the analyzer. Fastest to build.

2 — State Diagram → Code

Design a state transition diagram by hand, then write code that implements it directly. This is what the textbook example (front.c) does.

3 — State Diagram → Table

Design a state transition diagram by hand, then build a table that drives a generic interpreter. More flexible to modify.

Key helper functions in a lexical analyzer (front.c)
getChar()   — reads next char, sets nextChar and charClass (LETTER / DIGIT / UNKNOWN / EOF)
addChar()   — appends nextChar to the lexeme[] buffer
getNonBlank() — skips whitespace by calling getChar() in a loop
lookup(ch)  — maps single-char operators/parens to their token codes

/* Token codes defined as named constants (NOT raw numbers) for readability */

#define LEFT_PAREN  25

Reserved words and identifiers share the same pattern. The lexer recognizes both as IDENT, then uses a table lookup to check if the name is a reserved word. This avoids needing a huge state diagram.

4.3

The Parsing Problem

2 Goals of a Parser

1. Detect syntax errors and recover (so parsing can continue and find more errors).

2. Produce a parse tree (or trace of one) for syntactically correct input. This drives translation.

Parsing Complexity

A parser that works for any unambiguous grammar is O(n³) — impractically slow.

Parsers used in real compilers work on a subset of grammars and achieve O(n) — linear time. Speed is traded for some grammar restriction.

Top-Down vs Bottom-Up

Property Top-Down LL Bottom-Up LR
Tree direction Root → Leaves (top to bottom) Leaves → Root (bottom to top)
Derivation type Leftmost derivation Reverse of rightmost derivation
Scan direction Left to right Left to right
Implementation Recursive-descent (coded directly from grammar) LR parser with ACTION/GOTO tables
Left recursion ❌ NOT allowed — causes infinite recursion ✅ Allowed (handles it fine)
Grammar power Works on a subset of grammars LR grammars are a superset of LL grammars
Parsing task Choose which RHS to expand for leftmost nonterminal Find the handle in the current sentential form
LL vs LR naming
LL: Left-to-right scan, Leftmost derivation. LR: Left-to-right scan, Rightmost derivation (reversed). The first letter always means left-to-right scan.
4.4

Recursive-Descent Parsing

Core Idea
One subprogram (function) per nonterminal. Each function parses whatever its nonterminal generates. Functions call each other recursively, mirroring the recursive structure of the grammar. Based directly on EBNF rules.
EBNF Rule Parsing Function Behavior
<expr> → <term> {(+ | -) <term>} Call term(), then loop while next token is + or −: call lex() to consume the operator, call term() again.
<term> → <factor> {(* | /) <factor>} Call factor(), then loop while next token is * or /: call lex(), call factor() again.
<factor> → id | int_constant | ( <expr> ) If next token is IDENT or INT_LIT: call lex(). If next token is LEFT_PAREN: call lex(), call expr(), check for RIGHT_PAREN. Otherwise: error().
Recursive-descent function for <expr> (C)
void expr() {
    term();   /* parse first term */
    while (nextToken == ADD_OP || nextToken == SUB_OP) {
        lex();   /* consume + or - */
        term(); /* parse next term */
    }
}
/* Convention: when each function returns, nextToken holds
   the NEXT unused token. Every function starts assuming
   nextToken is already loaded. */
4.4.2

LL Grammar Restrictions

Problem 1 — Left Recursion

What it is: A rule where a nonterminal derives itself as the first symbol.

A → A + B (direct left recursion)
A → Ba, B → Ab (indirect left recursion)

Why it fails: The function for A immediately calls itself → infinite recursion / stack overflow.

Problem 2 — Pairwise Disjointness Failure

What it is: When two or more RHSs of the same nonterminal can begin with the same terminal symbol.

<var> → identifier | identifier [<expr>]

Why it fails: The parser can't decide which RHS to use just by looking at the next token.

Fixes

Problem Fix Example
Direct left recursion Eliminate left recursion: Replace A→Aα|β with A→βA′ and A′→αA′|ε E→E+T|T becomes:
E→TE′, E′→+TE′|ε
Pairwise disjointness failure Left factoring: Pull out the common prefix into a new rule <var> → identifier <new>
<new> → ε | [<expr>]
Pairwise disjointness failure EBNF extension: Use optional brackets to eliminate the problem without a new rule <var> → identifier [[<expr>]]
FIRST Sets & Pairwise Disjointness Test
FIRST(α) = the set of terminal symbols that can appear as the first symbol of any string derived from α.

The test: For each nonterminal A with multiple RHSs, for every pair of rules A→αᵢ and A→αⱼ:
FIRST(αᵢ) ∩ FIRST(αⱼ) = ∅ (empty set — no overlap allowed)

Example: A→aB | bAb | Bb, B→cB|d → FIRST sets are {a}, {b}, {c,d} → disjoint ✅ PASSES
4.5

Bottom-Up Parsing & LR

Handle

The specific substring of the current right sentential form that must be reduced to its LHS nonterminal to get the previous sentential form in the rightmost derivation.

The handle is always unique in any right sentential form. It equals the leftmost simple phrase.

Phrase

A string derived from a single internal node in the parse tree (one or more derivation steps from that node).

Multiple phrases can exist in one sentential form — one per internal node.

Simple Phrase

A phrase derived in exactly one derivation step. Always corresponds directly to a grammar RHS.

The leftmost simple phrase = the handle.

Shift-Reduce Actions

ActionWhat it does
Shift Push the next input token onto the parse stack (along with a state symbol)
Reduce The handle is on top of the stack. Pop it and push its LHS nonterminal. Use GOTO table to determine the new state.
Accept Parse is complete, no errors. Input was valid.
Error Syntax error detected. Call error-handling routine.

LR Parser Tables

ACTION Table

Rows: State symbols.
Columns: Terminal symbols (tokens).

Given current state + next input token → tells the parser to: Shift(Sn), Reduce(Rn), Accept, or Error.

GOTO Table

Rows: State symbols.
Columns: Nonterminal symbols.

Used after a reduction to determine which new state to push onto the stack. Row = state exposed after popping the handle. Column = LHS of the rule just reduced.

Knuth's Insight
The state symbol on top of the parse stack contains all the relevant information from the entire parse history. No matter how long the stack is, one state symbol summarizes what matters — keeping the number of distinct states small and manageable.

Advantages & Disadvantages of LR Parsing

Advantages

1. Can be built for all programming languages.

2. Detects syntax errors as soon as possible during left-to-right scan.

3. LR grammars are a proper superset of LL grammars — handles more grammars, including many left-recursive ones.

Disadvantage

The parsing table is very hard to construct by hand for a real programming language.

In practice, tools like yacc (Yet Another Compiler Compiler) generate the tables automatically from the grammar.

Key Questions & Short Answers

# Question Answer (concise)
Q1 What is the difference between a lexeme and a token? Lexeme = actual character string (e.g., "sum"). Token = numeric category code assigned to that lexeme (e.g., IDENT = 11).
Q2 Why are named constants used for token codes instead of numbers? For readability. Writing IDENT is clearer than 11 when reading lexer/parser code.
Q3 What is a state transition diagram? A directed graph (finite automaton) where nodes are states and arcs are labeled with input characters that cause transitions between states.
Q4 Why use character classes instead of individual characters in a state diagram? To simplify the diagram. Instead of 52 transitions for each letter, one LETTER transition handles all. Without classes, the diagram would be unmanageably large.
Q5 What are the two goals of syntax analysis? 1. Detect and report syntax errors (and recover). 2. Produce a parse tree (or its trace) for valid input.
Q6 What is left recursion and why does it break top-down parsers? A rule like A→Aα where A generates itself first. In recursive-descent, the function for A immediately calls itself → infinite recursion.
Q7 What is the pairwise disjointness test? For each nonterminal with multiple RHSs, check that FIRST(αᵢ) ∩ FIRST(αⱼ) = ∅ for every pair. If not empty, the parser can't choose the right RHS from one token of lookahead.
Q8 What is left factoring? A technique to fix pairwise disjointness failures. Pull out the common prefix of two or more RHSs into a new rule so FIRST sets become disjoint.
Q9 Define: phrase, simple phrase, handle. Phrase: Leaves of any subtree in the parse tree (1+ derivation steps). Simple phrase: Phrase derived in exactly 1 step (= a grammar RHS). Handle: The leftmost simple phrase = what to reduce next.
Q10 What mathematical machine underlies both top-down and bottom-up parsers? A Pushdown Automaton (PDA) — a finite automaton augmented with a pushdown stack.
Q11 Is left recursion a problem for LR parsers? No. Left recursion is only a problem for top-down (LL) parsers. LR (bottom-up) parsers handle left-recursive grammars fine.
Q12 Why do compilers not use O(n³) parsers? They are far too slow for practical use. Compilers restrict to grammar subclasses where O(n) parsing is possible — linearly faster at a cost of grammar flexibility.
