§ 8.1 Introduction
⚡ Core Result — Böhm & Jacopini (1966) Any algorithm expressible as a flowchart can be coded using only two control statements: (1) two-way selection and (2) logically controlled iteration. This proves the goto is mathematically unnecessary.
Concept Main Idea Key Detail
Control Statement Provides selection or iteration — the two extra mechanisms needed beyond assignment statements Without them, useful programs would be impossible
Control Structure A control statement plus the collection of statements it controls The broader unit including the body
Böhm & Jacopini Only 2 control statements are mathematically sufficient Makes goto nonessential (but not useless)
Writability vs. Readability More control statements → easier to write, harder to read (bigger language to learn) Too few → forces use of low-level goto, also hurts readability
The One Design Issue Should a control structure have multiple entries? Consensus: No — adds little flexibility, harms readability significantly
Multiple Entries Jumping into the middle of a control structure from outside it Only possible in languages with goto + statement labels
Multiple Exits Not a design issue — all languages allow them Safe as long as exit targets are immediately after the structure, not arbitrary locations
🎯 Possible Exam Question
"Böhm and Jacopini proved that only two control statements are necessary. What are they, and what does this imply about the goto?"
Answer: The two essential statements are (1) two-way selection and (2) logically controlled iteration. The implication is that the goto is superfluous — it is powerful and can build all other control structures, but it is not mathematically necessary. This fueled the debate about whether goto should be eliminated from languages entirely.
§ 8.2.1 Two-Way Selection Statements

General Form

All two-way selectors follow the same conceptual structure:

if control_expression
  then clause
  else clause

Three design questions determine how this plays out across languages.

Design Issue Options Language Examples
Control Expression Type Arithmetic only / Boolean only / Both C89 arithmetic only (0=false, nonzero=true)
C99/C++/Python both arithmetic & Boolean
Most modern Boolean only
Clause Form Single / Compound / Sequence Most languages single or compound (braces)
Perl always compound, even for one statement
Python/Ruby statement sequences + reserved word terminator
Python uses indentation + colon instead of then
Nesting / Dangling Else Rule-based / Syntax-based / Indentation Java/C/C++/C# else pairs with nearest unpaired then (rule)
Perl no problem — all clauses must be compound
Ruby end keyword closes each if explicitly
Python indentation determines pairing
ML no problem — else-less if not allowed

The Dangling Else Problem — Key Example

Ambiguous (Java/C) — else pairs with inner if by rule:

if (sum == 0)
  if (count == 0)
    result = 0;
  else           // ← pairs with inner if
    result = 1;

Force outer pairing in Java using braces:

if (sum == 0) {
  if (count == 0)
    result = 0;
}
else           // ← now pairs with outer if
  result = 1;

Ruby — unambiguous with end:

if sum == 0 then
  if count == 0 then
    result = 0
  end          // closes inner if — else below pairs with outer
else
  result = 1
end

Selector Expressions (Functional Languages)

In ML, F#, LISP — if is an expression that returns a value, not a statement. It can appear anywhere an expression can. In F#, both clauses must return the same type. If no else clause exists, the then clause can only return () — the unit type (no value).

let y =
  if x > 0 then x
  else 2 * x;;   // y gets x or 2*x depending on condition
🎯 Possible Exam Question
"What is the dangling else problem, and describe two different language design approaches used to solve it?"
Answer: The dangling else problem occurs when an else clause follows two nested then clauses with no intervening else, making it ambiguous which if the else belongs to.

Approach 1 — Static semantics rule (Java, C, C++): The else always pairs with the nearest previous unpaired then clause. Programmers must use braces to force the alternative interpretation.

Approach 2 — Required compound clauses (Perl): All clauses must always be wrapped in braces, so structure is always explicit and no ambiguity can arise.

Approach 3 — Closing reserved word (Ruby): Every if is explicitly closed with end, making it clear exactly which if each else belongs to.
§ 8.2.2 Multiple-Selection Statements
⚡ Key Idea A multiple-selection statement is a generalization of the two-way selector — it chooses one of any number of paths. Although it could be built from nested if-else + goto, the result would be unreadable and unreliable.
Language Statement Control Expression Type Fall-Through? Key Distinction
C / C++ switch Discrete (int, char, enum) ✅ Yes — needs explicit break No implicit branches; case labels treated like normal statement labels — can appear almost anywhere
Java switch Discrete (int, char, enum, String) ✅ Yes — needs explicit break Case expressions only allowed at top level of switch body — no complex nesting like C
C# switch Discrete + String ❌ No — static rule requires explicit break or goto Every segment must end with unconditional branch; control expression can be a string
PHP switch Any scalar: string, int, double ✅ Yes — needs explicit break More type flexibility than C — allows doubles and strings as case values
Ruby case Boolean expressions ❌ No Returns a value (it's an expression); evaluates Boolean conditions top to bottom
Perl / Python — — — No multiple-selection statement — use else-if instead

C switch — Fall-Through Problem

Without break — falls through everything:

switch (index) {
  case 1:
  case 3: odd++;
          sumodd += index;
  case 2:
  case 4: even++;  // always runs!
  default: printf("Error\n"); // always runs!
}

With break — restricted to one segment:

switch (index) {
  case 1:
  case 3: odd++;
          sumodd += index;
          break;
  case 2:
  case 4: even++;
          break;
  default: printf("Error\n");
}

Note: empty cases 1 and 3 intentionally fall through to share code with cases 3 and 4. This is the flexibility the design offers — at the cost of reliability.

Implementing Multiple Selection — Compiler Strategies

SituationStrategyPerformance
Few cases (<10) Conditional branches or linear search on table ~N/2 tests on average — simple but slow for large N
Many cases (≥10) Hash table of segment labels Near-constant time for any case
Range-based cases (e.g. Ruby) Binary search table O(log N) — hash doesn't work with ranges
Dense case values (>50% of range covered) Array indexed by case value, values are segment labels O(1) array lookup — fastest possible

else-if / elif — Not Redundant with switch

When selection depends on Boolean expressions rather than a single discrete value, switch is inadequate. else-if handles this and is more general.

Python elif:

if count < 10:
    bag1 = True
elif count < 100:
    bag2 = True
elif count < 1000:
    bag3 = True

Scheme COND:

(COND
  ((> x y) "x greater")
  ((< x y) "y greater")
  (ELSE   "equal")
)

Scheme's COND evaluates predicates top-to-bottom; returns the expression of the first true predicate. Always include ELSE — without it, if no predicate is true the result is unspecified.

🎯 Possible Exam Question
"Explain the fall-through behavior of C's switch statement. What problem does it create, and how does C# solve it differently?"
Answer: C's switch has no implicit branches at the end of each selectable segment. Once a matching case is found, execution continues into the next segment unless an explicit break is used. This was intentional — it allows multiple case values to share code via empty cases. However, a forgotten break silently causes wrong behavior, creating a reliability problem.

C# solves this with a static semantics rule requiring every segment to end with an explicit unconditional branch — either break (exits switch) or goto case (jumps to another segment). This makes accidental fall-through impossible while still allowing intentional transfers.
§ 8.3.1 Counter-Controlled Loops
⚡ Terminology Loop variable = holds count value · Loop parameters = initial value, terminal value, stepsize · Pretest = condition checked before body · Posttest = condition checked after body
Language Syntax Loop Variable Changeable? Parameters Evaluated Value After Termination Key Feature

C99 / C++ for(int i=0; ...) ✅ Yes Same as C Out of scope after loop Can declare variable inside first expression; scope is loop body only
Java / C# Like C++ ✅ Yes Same as C Out of scope Control expression must be boolean (not arithmetic)

C for — Operational Semantics

// for (e1; e2; e3) { body }
e1
loop:
  if e2 == 0 goto out
  [loop body]
  e3
  goto loop
out: ...

All three expressions are optional. An absent e2 is treated as true → potentially infinite loop. Legal to branch into the loop body (though dangerous).

F# Counter Loop via Recursion

let rec forLoop loopBody reps =
  if reps <= 0 then
    ()          // unit type — "do nothing", required because F# has no empty statement
  else
    loopBody()
    forLoop loopBody (reps - 1);;

rec marks the function as recursive. Every if must have an else in F#, hence the () unit type placeholder.

§ 8.3.2 Logically Controlled Loops
⚡ Key Fact Logically controlled loops are more general than counter-controlled — every counting loop can be built with a logical loop, but not vice versa. These are one of the two structures proven essential by Böhm & Jacopini.
Form Language Syntax Body Executes Min. Control Expression Can Branch Into Body?
Pretest C / C++ while (expr) body 0 times C89: arithmetic; C99+: arithmetic or Boolean ✅ Yes (legal in C/C++)
Posttest C / C++ do body while (expr); 1 time (always) Same as above ✅ Yes
Pretest Java while (expr) body 0 times Boolean only ❌ No (no goto in Java)
Posttest Java do body while (expr); 1 time Boolean only ❌ No
Pretest (simulated) F# (functional) Recursive function 0 times A boolean-returning function N/A

⚠️ Posttest Danger

Posttest loops always execute the body at least once, even if the condition is false from the start. This is a common source of bugs — programmers sometimes forget this behavior. The syntactic placement of the condition after the body helps remind the reader, but it remains a source of errors.

// do-while operational semantics:
loop:
  [loop body]               // always runs first
  if control_expression goto loop

F# Logical Loop Simulation

let rec whileLoop test body =
  if test() then
    body()
    whileLoop test body
  else
    ();;
§ 8.3.3 User-Located Loop Control Mechanisms
Statement Language Type Effect Can Exit Multiple Loops?
break C, C++, Python, Ruby, C# Unconditional, unlabeled Exits the innermost enclosing loop immediately ❌ No — innermost only
break label Java Unconditional, labeled Exits the loop named by the label — can be an outer loop ✅ Yes
last Perl Unconditional, labeled Same as Java's labeled break ✅ Yes
continue C, C++, Python Unconditional, unlabeled Skips rest of current iteration, transfers to loop control — does not exit the loop ❌ Not an exit

Java Labeled break — Exiting an Outer Loop

outerLoop:
for (row = 0; row < numRows; row++)
  for (col = 0; col < numCols; col++) {
    sum += mat[row][col];
    if (sum > 1000.0)
      break outerLoop;  // exits the outer for, not just the inner
  }

continue vs break

continue — skips rest of body, checks condition again:

while (sum < 1000) {
  getnext(value);
  if (value < 0) continue;
  sum += value;  // skipped if negative
}

break — exits the loop entirely:

while (sum < 1000) {
  getnext(value);
  if (value < 0) break;
  sum += value;  // loop is over if negative
}
⚡ These are camouflaged gotos — but safe ones break/continue/last are restricted gotos. Their targets must be below the exit and only immediately after a loop body — unlike real goto which can jump anywhere. This restriction preserves readability. In fact, avoiding them would result in more convoluted code.
§ 8.3.4 Iteration Based on Data Structures
⚡ Key Property of an Iterator An iterator must be history sensitive — it must remember which element it last returned so it can visit every element exactly once without repetition. The loop terminates when the iterator finds no more elements.
Language Mechanism Syntax / Example Key Notes
Java 5.0+ Enhanced for (foreach) for (String e : myList) { ... } Works on arrays and any collection implementing Iterable. All predefined generic collections implement it.
C# foreach foreach (String name in names) Console.WriteLine(name); All generic collections (List, Stack, Queue, Dictionary) have built-in iterators. Users can implement IEnumerator for custom iterators.
Ruby Blocks + each list.each {|value| puts value} Block is an anonymous method passed as a parameter. |value| is the block parameter. yield inside a method calls the attached block.
Ruby times 4.times {puts "Hey!"} Sends the block to the integer object. Returns the receiver (4 in this case).
Ruby upto 1.upto(5) {|x| print x, " "} Ruby has no real for statement — for loops are converted to upto calls internally.
Python Generator / yield yield nod inside a method Any method with yield is a generator. On each call, resumes from where it left off rather than restarting. Local state is preserved across calls.

Python Generator — How yield Works

class MyStructure:
  def traverse(self):
    # if there is another node, set nod to next node
    yield nod   # returns nod, then RESUMES HERE on next call

Unlike a regular return, yield suspends the function and saves its state. The next call picks up exactly where it left off. This makes it naturally history-sensitive without storing all elements in memory first.

🎯 Possible Exam Question
"What is an iterator in the context of data structure-based iteration, and what is the key property it must have? Give an example from any language."
Answer: An iterator is a user-defined function used in data structure-based iteration that returns the next element of a data structure each time it is called. Its essential property is that it must be history sensitive — it must remember which element it last returned so it can visit every element exactly once and detect when no more remain.

Example — Python generator: A method containing yield acts as an iterator. On the first call, it returns the first node. On subsequent calls, execution resumes from where it left off (after the yield), returning the next node. Local state is preserved across calls, making it naturally history-sensitive.
§ 8.4 Unconditional Branching (goto)
Concept Main Idea Key Detail
goto Power Most powerful flow control — can build all other control structures from goto + selector This power is exactly what makes it dangerous
goto Danger Can force any statement to follow any other regardless of textual order Readability is best when execution order ≈ textual order (top to bottom)
Dijkstra (1968) First widely-read argument against goto — called it "too primitive" Sparked major debate in computing; argued for restricting or eliminating goto
Knuth (1974) Argued against complete elimination Said there are occasions where goto's efficiency outweighs its harm to readability
Partial Restriction Restricting goto to transfer control only downward partially alleviates the problem Allows error handling but prevents building loops
Languages without goto Java, Python, Ruby Provide additional control statements (loop exits) to cover legitimate goto use cases
Languages with goto C, C++, C# (and most popular languages) C's designers called it "infinitely abusable" yet kept it; C# includes it even though Java doesn't
Loop Exits as goto break, continue, last are camouflaged gotos But severely restricted — targets must be below the exit and only after a loop. Do NOT harm readability.
🎯 Possible Exam Question
"Why is the goto statement considered dangerous, and what was the main conclusion of the historical debate around it?"
Answer: The goto is dangerous because it can transfer control to any statement anywhere in the program regardless of textual order, severely harming readability. Readability is best when execution order matches textual top-to-bottom order, and unrestricted gotos destroy this property, making programs unreliable and costly to maintain.

The historical debate, sparked by Dijkstra's 1968 letter, concluded that while goto is mathematically unnecessary (Böhm & Jacopini), complete elimination is not always justified. The practical resolution was: languages without goto should provide additional restricted control statements (like loop exits) to handle legitimate goto use cases, and if goto is included, restricting it to transfer control only downward partially alleviates the readability problem.
